# Phase 4.1 — Contract lifecycle management

Closes ERP domain #17 ("Contracts management — connected to Documents, not a
second document system"). Built **on** Documents, Workflow, Contacts and the
domain-event bus; nothing here duplicates any of them.

## The point of the feature

`contracts.notice_by` — the last day notice can be served, stored rather than
derived. Every other design decision follows from it:

- The column is written by `Contract::booted()` on **every** save, from
  `noticeDeadline()`. There is one definition of the date and no writer can
  forget to update it after moving an end date.
- Stored so it can be indexed, sorted and queried. Computed on read it would be
  equally correct and completely useless — nothing could ask "whose deadline
  falls this fortnight" without loading every contract in the business.
- `raise()` **refuses** an auto-renewing contract with an end date and no notice
  period. That combination produces no date anyone could be warned about, so it
  rolls over in silence forever — the exact failure this module exists to stop.
- `ContractWatch` keeps "coming up", "already gone" and "already gone AND it
  renews itself" as three separate lists, on the reasoning
  `BusinessDocument::scopeExpiringWithin` already uses for expired documents.

## Platform services extended, not duplicated

| Concern | Where it lives | What contracts do |
|---|---|---|
| The signed paper | `business_documents` | `Contract::papers()` reads through `business_document_relations`; attach with the existing `DocumentLinker`. No body, no file path, no PDF store here. |
| Numbering | `BusinessDocumentNumberingScheme` | `contracts` has **no** `number` column. `Contract::reference()` reads the paper's. There is a test asserting the column does not exist. |
| E-signature, versions, sharing, retention | Documents | Inherited by the paper. Nothing re-implemented. |
| Approval | `WorkflowEngine` + `Approvable` | `submit()` calls `WorkflowEngine::start()`. There is deliberately no `approve()`/`reject()` on the service, and a test asserts their absence. |
| Counterparty | `contacts` | `contact_id`, nulled on delete. No second customer/supplier list. |
| Audit | `activity_log` / domain events | Events emitted at the point the thing happens, inside the service. |

## Permission keys to add to `App\Support\Permissions`

Suggested `contracts` group:

| Key | Reasoning |
|---|---|
| `contracts.view` | Reading the register is not reading the paper. A contract's terms (value, notice date) are commercially sensitive but far less so than the signed document, which is already protected by `BusinessDocumentPolicy` and its security levels. Separating them lets an operations manager see what expires when without being handed every confidential agreement. |
| `contracts.manage` | Raise, edit, add obligations, submit for approval. The everyday working permission. |
| `contracts.renew` | Split from `manage` deliberately: renewing commits the business to another term and another year of spend. The person who maintains the register is often not the person entitled to commit to it. |
| `contracts.terminate` | Same reasoning in the opposite direction, and with legal consequences. Ending a contract early can trigger a penalty clause. |

Approving is **not** a contracts permission — being assigned by the engine is
the authorisation, exactly as for expense claims and documents.
`WorkflowInboxTest::test_approving_does_not_require_a_workflow_permission` is
the precedent.

`/contracts/watch` should be the module's landing screen, not `/contracts`. A
register opens on the list of everything by default and everything is where the
notice deadlines get lost; `ContractWatch::summary()` is designed to be the
header of that screen and to feed a dashboard tile.

The `/actions` inbox already picks up contract approvals with no change —
`Approvable` is all it needs.

## `config/modules.php` placement

Suggested key `contracts`, with `requires => ['contacts']` and
`switchable => true`.

Reasoning: a contract without a counterparty is a note to self, so the contacts
dependency is real in the way `Modules::enabled()` means it — the screen cannot
work without it. It is **not** dependent on `documents`: a business can run a
useful contract register recording terms and notice dates before it has put a
single PDF into Documents, and forcing Documents on to get expiry alerts would
be a worse product than letting the paper arrive later.

It is switchable, unlike Workflow. Contracts is a module, not a platform
service — no other module reads from it, so switching it off costs nothing
elsewhere.

## Domain events to add to `App\Support\DomainEvents::CATALOGUE`

New `contract` group. The events are already emitted; they just cannot be picked
from an automation rule's trigger list until the catalogue names them.

```
contract.raised
contract.activated
contract.renewed
contract.terminated
```

`Contract::automatableFields()` allows `description`, `notes`, `owner_id`,
`type` only. Dates, value and status are excluded on purpose: they are what the
business agreed and what the register reports, and an automation rule must not
be able to move a notice deadline.

## Things a reviewer should challenge

1. **Approval auto-activates the contract.** `ActivateApprovedContracts` puts an
   approved contract straight into force. The argument: an approved contract
   left in draft is binding on paper and invisible to every expiry and notice
   warning — a worse failure than activating slightly early, which a business
   can express with a later `starts_on`. The counter-argument is that "approved"
   and "signed" are genuinely different events and this conflates them. If the
   product later grows a signature-completion trigger, activation should
   probably move there.

2. **`activate()` ignores `starts_on`.** A contract starting next month can be
   activated today, and `ContractWatch` will list it. Deliberate — the notice
   deadline on a future contract still matters — but it means "active" reads as
   "in the register and being watched", not "in force today".

3. **`raise()` refuses auto-renewal without a notice period.** A validation rule
   inside a service, which is unusual for this codebase. Justified because it is
   the one data shape that silently defeats the whole feature, but it will annoy
   somebody importing a legacy register. An importer may need a way past it.

4. **`notice_by` is stored, and `Contract::booted()` writes it on every save.**
   A mass `Contract::query()->update(['ends_on' => …])` would bypass the hook
   and leave the deadline stale. No such call exists today. If bulk date edits
   are ever added, they must go through the model.

5. **`expired` is a swept status, not a computed one.**
   `ContractLifecycle::expireLapsed()` exists but nothing schedules it — there
   is no scheduled job for this module yet, the same gap Documents has for
   signature reminders. Until something calls it, `ContractWatch::lapsed()` is
   the honest answer and `expired` will rarely appear.

6. **No `ContractPolicy` and no Livewire screens.** Service and read-model only,
   per the brief's file-ownership rule. The policy will need
   `BusinessDocumentPolicy` as its precedent for how the paper's security level
   interacts with `contracts.view`.

7. **Obligations have no recurrence.** "Monthly deep clean" has to be entered
   twelve times. A `recurrence` column was considered and left out: the moment
   it exists something has to generate the instances, and that is a scheduled
   job this module does not yet have.

8. **`Contract::papers()` is not a relation.** It is a method returning a
   collection, because the morph goes through `BusinessDocumentRelation` rather
   than directly. Eager-loading contracts with their papers is therefore an
   N+1 waiting to happen on a list screen; use `documentRelations` for that.

9. **`counterparty()` rather than `contact()`.** `contact_id` would not actually
   have shadowed `contact()`, so the rename is for readability rather than for
   safety. Named here so nobody "fixes" it back.

## Addendum — the Livewire screens

`App\Livewire\Contracts\Index` + `resources/views/livewire/contracts/index.blade.php`
`App\Livewire\Contracts\Show` + `resources/views/livewire/contracts/show.blade.php`
`tests/Feature/Contracts/ContractScreensTest.php` (12 tests). Full `Contract`
filter: 62 passed.

**Index** is the watch screen and the register on one page, watch first. The
auto-renewing-with-notice-missed list is rendered as a bordered alarm block
above everything, not as a table row; the other two missed/lapsing lists are
ordinary panels side by side. Below that, search + status pills + the register.
Raising happens here.

**Show** leads with the notice date — above the value and above the dates it is
derived from — then the terms, the paper (the shared
`<x-documents.library-panel>`, titled "The paper"), obligations, and the renewal
history. Submit, renew, terminate and the obligation forms live here. No approve
button anywhere.

Every state change goes through `ContractLifecycle`; every `RuntimeException` is
caught and shown through `addError` on the form it came from.

### Routes to register

```php
Route::get('/contracts', App\Livewire\Contracts\Index::class)
    ->name('contracts.index')
    ->middleware('can:contracts.view');

Route::get('/contracts/{contract}', App\Livewire\Contracts\Show::class)
    ->name('contracts.show')
    ->middleware('can:contracts.view');
```

`contracts.index` is the landing screen and carries the watch, so no separate
`/contracts/watch` is needed — the earlier suggestion above is superseded.

### Navigation entry for `config/opes.php`

```php
['key' => 'contracts', 'label' => 'Contracts', 'icon' => 'document-check', 'route' => 'contracts.index', 'ability' => 'contracts.view'],
```

The layout is called with `['title' => …, 'active' => 'contracts']`, so the key
must be `contracts`.

### What the backend made awkward

1. **Nothing gives the view a link.** Until the routes above land, `route()`
   would throw and take the whole watch screen down, so both views guard with
   `Route::has(...)` and fall back to plain text. **Delete those guards once the
   routes are registered** — they are scaffolding, not a pattern.

2. **`renew()` will not extend an expired contract.** It requires `active`, but
   nothing schedules `expireLapsed()`, so in practice a contract sits `active`
   past its end date and renewal still works. The day a scheduled sweep is added,
   the ordinary "we renewed it late" case starts being refused. Worth deciding
   then whether `renew()` should accept `expired`.

3. **`Contract::papers()` is not a relation**, so the register cannot show which
   contracts have their signed copy attached without an N+1. The list screen
   deliberately does not try; `reference()` is shown on Show only.

4. **`daysToNotice()` needs `notice_by`,** which is null on an open-ended
   contract — every date on both screens is null-guarded for that case.
