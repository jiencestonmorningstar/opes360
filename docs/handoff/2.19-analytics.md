# 2.19 — Documents analytics

## What shipped

- `app/Support/DocumentAnalytics.php` — the read model. Per period: created/issued
  counts (total and by kind), average draft→issue days, approval bottlenecks read
  from the workflow engine's own instances and decisions, signature completion
  rate and average hours-to-sign, external share-link opens and the papers that
  travel most, expiring-soon count, and storage (filed bytes) by folder.
- `app/Livewire/Papers/Analytics.php` + `resources/views/livewire/papers/analytics.blade.php`
  — the screen, in the Executive screen's house style (range pills, KPI cards,
  tables).
- `tests/Feature/Documents/DocumentAnalyticsTest.php` — 13 tests, all figures
  checked against direct queries.

## Route line to add (routes/web.php is out of my ownership)

```php
Route::get('/library/analytics', PapersAnalytics::class)->middleware('can:papers.manage')->name('papers.analytics');
```

with `use App\Livewire\Papers\Analytics as PapersAnalytics;`. Register it ABOVE

## The gate argument (papers.manage, not papers.view)

This screen aggregates across every document in the company, including
restricted ones' metadata — their counts, share-open tallies, filed bytes. A
`papers.view` holder only ever sees lists narrowed by `readableBy()`; giving
that person totals over the unnarrowed table would let them learn what the
lists refuse them (that restricted papers exist, how many, how often they
travel). `papers.manage` is exactly the ability that already opens restricted
documents, so these aggregates reveal nothing its holder could not read
directly. Even so, restricted titles never appear in any payload — only
counts, under the generic label "Restricted document" — because numbers from
this screen get pasted into slides whose audience is not the audience of the
gate. A test asserts the title appears nowhere in the JSON of every method.

## Deliberately not counted, and why

- **Composed body text as storage.** Bodies are database rows, not files on the
  documents disk; adding character counts to media bytes is adding metres to
  litres. "Storage by folder" means filed binaries (the `media` rows
  DocumentFiler writes).
- **Version rows, comments, or audit rows as storage.** Same reasoning — they
  are relational data, and counting them as "storage used" would tell an
  administrator nothing actionable about disk.
- **`submitted` decisions in bottleneck timing.** Submission is the run
  starting, not a step concluding; counting it would credit the first step with
  a zero-length stay it never had.
- **Expired documents inside "expiring soon".** The model's own
  `scopeExpiringWithin` excludes them on purpose (missed deadlines are a
  different list); the dashboard repeats the scope rather than re-deriving it.
- **Expiring-soon and storage are not windowed.** They are facts of right now —
  a balance, not a flow — and pretending they reset with the date filter would
  be the same lie the Kpis class documents for cash position.
- **A prior-period delta set.** Kpis earns its deltas because money has a
  meaningful "versus last month"; document counts this early would mostly
  compare small integers to zero and print "No prior figure" six times. Easy to
  add later by instantiating a second `DocumentAnalytics` on
  `previousWindow()`.

## Portability and tenancy notes

- All period bounds are instants (`startOfDay`/`endOfDay`), so a document
  issued at 23:50 on the window's last day counts — tested.
- Every average is computed in PHP off timestamps; no `DATE_FORMAT`/`julianday`
  anywhere, so SQLite tests exercise the same SQL MySQL runs.
- Tenancy is the `BelongsToCompany` global scope throughout; the one unscoped
  table (`business_document_share_accesses`) is reached only through a
  subquery on the scoped shares table. A test creates a busy second company
  and asserts every aggregate stays at the first company's figures.
