# Phase 4.3 — BI & Analytics: integration notes

## What shipped

- **`App\Support\Kpis`** — the executive KPI read model. Per-period figures with a
  length-matched prior period and percentage deltas (`summary()`), plus
  `customerProfitability()`, `projectBudgets()` and `stalledApprovals()`.
- **`App\Livewire\Reports\Executive`** + `resources/views/livewire/reports/executive.blade.php`
  — the executive screen: KPI cards with deltas, point-in-time balances, the
  "needs eyes today" alarm list (each row links to its own screen), revenue by
  customer, and project budget consumption.
- **`tests/Feature/Reports/ExecutiveTest.php`** — 13 tests. The load-bearing ones
  assert *agreement*: each KPI equals what the underlying report returns for the
  same window (sales report query, `Books::incomeStatement`, `CashForecast::currentCashPosition`,
  `Aging::receivable`). Plus the date-cast last-day pitfall, tenancy isolation,
  delta-from-zero, and the weighted days-to-payment arithmetic.

## The non-negotiable rule, honoured

Every figure is read through the class that owns it; this phase added **no new
methods to any existing class** because nothing was missing:

| KPI | Source |
|---|---|
| Revenue / invoice count | the exact `Document::invoices()->issuedBetween()` query `Reports\Index` runs |
| Collected | `Payment` sum over `received_at`, as `Reports\Index` |
| Expenses | recorded non-void `Expense` totals, mirroring the home dashboard tile |
| Net result | `Books::incomeStatement()['resultat']` — the books' own answer, not documents minus expenses |
| Cash position | `CashForecast::currentCashPosition()` |
| Receivables outstanding / overdue share | `Aging::receivable()` totals (overdue = total − current bucket) |
| Payables due soon | `PaymentSchedule::bills()` filtered to its own OVERDUE/DUE_SOON bands (14-day horizon) |
| Alarms | `ComplianceCalendar::summary()`, `ContractWatch::summary()`, `SlaBoard::summary()`, `WorkflowInstance` status `stalled` |

One near-miss worth recording: the Kpis expense sum initially copied the home
dashboard's `whereBetween` on date *strings*, which drops the last day of the
period against the datetime-backed `issue_date` column. The test caught it;
Kpis binds on Carbon start/end-of-day instants. The home dashboard's own tile
(`app/Livewire/Dashboard.php`, `counters()`) still uses string bounds and may
undercount month-end expenses — out of my file ownership, flagged here.

## Deliberately NOT computed

- **Gross margin / COGS.** COGS is not posted to the ledger when an invoice is
  issued, and deriving it from `StockValuation`'s *current* weighted-average
  cost would restate history every time a supplier price moved. A margin that
  changes retroactively is worse than none. If invoice-time COGS posting ever
  lands in `RecordsBusinessEvents`, the margin becomes a one-line read of the
  income statement's class-60x accounts.
- **Pipeline weighted value.** No `SalesForecast` class existed at build time
  (checked; only `CashForecast`). When one lands, `Kpis` should repeat its
  figure, not build its own.
- **Profit by customer / by project.** Cost is not recorded against customers
  anywhere; documents carry no `project_id`. The screen shows what the data
  genuinely knows: revenue/collected/outstanding per customer, and budget vs
  `Project::costToDate()` consumption per project. Spreading overheads to fake
  a margin would be an allocation argument dressed as a report.

## Permission

`reports.view` suffices. The screen shows only figures already visible on the
reports it summarises (aging, sales, books), so a new key would gate nothing
new; the alarm links land on routes that carry their own `compliance.view`,
`contracts.view`, `service.view` middleware, so a reader without those rights is
stopped at the destination, which is where the detail lives.

## Caching notes (the dashboard-load question)

The screen currently runs roughly: 2× windowed KPI sets (≈8 queries each),
`Books::trialBalance` twice via incomeStatement (2× per period), one full
`Aging::receivable()` + `payable()` load, compliance/contract/SLA count queries
(~12 cheap counts), customer aggregate (2), and `costToDate()` per listed
project (2 each, capped at 8 projects). Fine for the current scale; before this
becomes a most-loaded screen:

1. Cache `summary()` per company+range for ~5 minutes (`Cache::remember`,
   key `kpis:{company}:{range}:{date}`) — every figure is a photograph anyway.
2. The prior-period half never changes intraday; it could cache for the day.
3. `projectBudgets()` is the only N+1-ish part; a `withSum` on time entries and
   expenses would collapse it to 3 queries if project counts grow.
