a single known supplier; it does **not** skip the approval.

## 1. The listener registration line (please add)

In `app/Providers/AppServiceProvider.php`, beside the existing
`PostApprovedExpenseClaims` registration:

```php
use App\Listeners\SyncApprovedRequisitions;

Event::listen(DomainEvent::class, SyncApprovedRequisitions::class);
```

Until that line exists, an approved requisition's `status` column stays at
`submitted`. Nothing unsafe follows from that — every gate in `Sourcing` asks
`PurchaseRequisition::isApproved()`, i.e. the engine, never the column — but
list screens will read wrong.

The test registers the listener in its own `setUp()` with a comment pointing
here. Once it is in the provider that line can be deleted.

## 2. The approval engine was reused, not rebuilt

- `PurchaseRequisition` uses `App\Models\Concerns\Approvable`. That is the
  whole integration.
- `Requisitions::submit()` calls `WorkflowEngine::start()` and returns the
  instance. There is **no** `approve()`, no `reject()`, no approval status
  machine, and a test asserts by reflection that no such method exists.
- The verdict arrives on the generic `workflow.approved` / `.rejected` /
  `.cancelled` / `.changes_requested` events, via a listener — exactly the
  `PostApprovedExpenseClaims` pattern. The engine was not taught that
  requisitions exist.
- The threshold rule is configuration. A test proves "over 10,000,000 needs
  the director" works as a step condition
  (`['field' => 'estimated_total', 'operator' => '>=', 'value' => 10000000]`)
  with no code in this module aware of it.

`workflow.changes_requested` maps to a **`returned`** status, not `rejected`.
"No" and "not yet" are different answers.

## 3. A default workflow needs seeding

`Workflow::defaultFor(PurchaseRequisition::class)` returns null until an
administrator defines one, and `submit()` throws rather than approving
silently. Suggested seeded default:

- Step 1 — approval, `approver_mode: manager`, quorum `any`
- Step 2 — approval, `approver_mode: owner`, quorum `any`,
  condition `estimated_total >= 10000000`

## 4. Permissions to add (`app/Support/Permissions.php` + `RolePermissionSeeder`)

- `procurement.requisitions.view`
- `procurement.requisitions.manage` — raise and submit a requisition
- `procurement.rfqs.view`
- `procurement.rfqs.manage` — open an RFQ, invite suppliers, record quotations
- `procurement.rfqs.award` — choose a quotation and raise the order

Suggested roles: staff gets `requisitions.view` + `requisitions.manage` (asking
for something is not spending); manager adds the RFQ pair; owner/admin add
`award`. Note that **approving** needs no permission — being asked is the
permission (`docs/workflows.md`).

Nothing decides approver identity from these; they gate screens only.

## Decisions worth a look

1. **The award produces a *draft* purchase order, unnumbered.** Awarding is a
   sourcing decision; issuing is a commitment. The PO number is left to the
   code that owns the sequence — handing one out at award time would burn a
   number every time somebody changed their mind, and a PO sequence with holes
   in it is the first thing an auditor asks about. If you want award-to-issued
   in one step, call the existing issuer after `Sourcing::award()`.
2. **A supplier who was not invited cannot quote.** Enforced, not warned. The
   trail has to show every price considered was solicited.
3. **`compare()` ranks on price only.** Lead time and payment terms are stored
   on every quotation for the buyer to weigh; a weighted score the buyer cannot
   see would be a purchasing decision made by software.
4. **`SupplierQuotation` is not a `Document`.** A `Document` is paper this
   business issued and is answerable for, and issued documents are immutable
   and numbered by us. A supplier's quote keeps *their* reference and never
   enters our numbering sequence.
5. **Suppliers are `Contact` rows throughout.** No parallel supplier list; a
   contact from another tenant is refused explicitly on invite and on
   `orderDirect()`.
6. **`orderDirect()` exists.** Single known supplier, small amount, emergency —
   a real path. It skips the market test, never the approval.
7. **Numbers (`PR-YYYY-nnnn`, `RFQ-YYYY-nnnn`) come from the highest issued,
   not a row count** — a soft-deleted row still holds its number under the
   unique index, and counting would reissue it. If you would rather these went
   through `DocumentNumbers`, the two `nextNumber()` methods are the only
   places to change.

# Phase 3.5 — the two screens (front-end handoff)

New files only. No routes, config, permissions, seeders, guides or provider
edits were touched.

| File | What it is |
| --- | --- |
| `app/Livewire/Procurement/Requisitions.php` + `resources/views/livewire/procurement/requisitions.blade.php` | Raise a requisition with lines, submit it, see where it got to |
| `app/Livewire/Procurement/Sourcing.php` + `resources/views/livewire/procurement/sourcing.blade.php` | Open an RFQ, invite suppliers, record quotations, compare, award |
| `tests/Feature/Procurement/ProcurementScreensTest.php` | 6 tests, 31 assertions |

Both screens call the services only, catch `RuntimeException` and surface it
with `addError`, and gate every action on the `procurement.*` abilities already
in the catalogue. Neither has an `approve()` method and neither renders an
approve or reject control — a submitted requisition is decided at `/actions`,
and a test asserts the absence rather than trusting the review.

## 1. Route lines to add (`routes/web.php`, in the authenticated group)

Beside the other module screens:

```php
use App\Livewire\Procurement\Requisitions as ProcurementRequisitions;
use App\Livewire\Procurement\Sourcing as ProcurementSourcing;
```

```php
Route::get('/procurement/requisitions', ProcurementRequisitions::class)
    ->middleware('can:procurement.requisition-view')->name('procurement.requisitions');
// Gated on rfq-view, not rfq-manage: a buyer's manager needs to read the
// comparison without being the person who invites or awards.
Route::get('/procurement/sourcing', ProcurementSourcing::class)
    ->middleware('can:procurement.rfq-view')->name('procurement.sourcing');
```

The two screens link to each other, but each link is wrapped in
`Route::has(...)` so nothing breaks before those lines exist. The wrappers can
be dropped once they do.

## 2. Nav entries to add (`config/opes.php`, `navigation`)

```php
['key' => 'procurement', 'label' => 'Requisitions', 'icon' => 'clipboard', 'route' => 'procurement.requisitions', 'ability' => 'procurement.requisition-view'],
['key' => 'procurement', 'label' => 'Sourcing', 'icon' => 'clipboard', 'route' => 'procurement.sourcing', 'ability' => 'procurement.rfq-view'],
```

Both use `'active' => 'procurement'` in their layout call, so either entry
highlights while the user is anywhere in the module. The abilities carry the
module switch (procurement ships off), so a business that has not turned it on
never sees either row.

## 3. Still outstanding from the sections above

Neither screen works end to end until the earlier items are done: the
`SyncApprovedRequisitions` listener registration (§1), the seeded default
workflow (§3, and it must be the `is_default` one — `submit()` throws
otherwise), and the role grants for the `procurement.*` abilities (§4). Until
the grants exist only the Owner can open either screen.
