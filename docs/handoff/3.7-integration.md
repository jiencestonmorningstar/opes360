# Phase 3.7 — CRM completion: integration notes

Closes checklist row 7 (Sales & CRM): leads as a distinct entity, activity
logging against deals, and sales forecasting.

## What shipped

**Leads** — `App\Models\Lead` + `App\Services\LeadFunnel`. A lead is a name
and a number that might become a customer, kept OUT of the customer book until
it earns a place there. Statuses: new / working / qualified / converted /
lost. Converting creates a `Contact` (and optionally a `Deal` through the
existing `DealPipeline`) and links back via `contact_id` / `deal_id`; the lead
row survives as the record of where the customer came from. Losing requires a
reason. Terminal states are unreachable by a plain status move — only
`LeadFunnel::convert()` / `lose()` write them, so the links and the reason
cannot drift from the status.

**Deal/lead activities** — `App\Models\CrmActivity` (`crm_activities`),
polymorphic over Deal and Lead. Kinds: call / meeting / note / task. Two
timestamps (`due_at`, `done_at`) instead of a status column: "due and not
done" *is* overdue. `CrmActivity::log()` is the one write path; a row with no
due date is done the moment it is written. Scopes: `planned()`, `overdue()`.

**Forecast** — `App\Support\SalesForecast`, a pure read in the `Aging` /
`CashForecast` style. Weighted pipeline = value × win probability, bucketed by
expected close month, split per owner. Probability comes from
`Deal::STAGE_PROBABILITIES` (lead 10, qualified 30, proposal 60) unless the
new nullable `deals.probability` column overrides it (`Deal::winProbability()`).
Bucketing is done in PHP off the cast date, deliberately — a date cast stores
midnight and a naive `whereBetween` on month bounds drops the last day of the
month. Overdue-but-open deals roll into the current month; no-date deals get
an explicit "unscheduled" row rather than vanishing.
`SalesForecast::untouchedDeals($days)` is the "deals nobody has touched"
query: open, no activity in the window, record itself unwritten.

**Screen** — `App\Livewire\Leads\Index` + `resources/views/livewire/leads/index.blade.php`,
one register with three tabs (Leads / Activity / Forecast), in the Assets
Movements style: inline forms, service calls with `addError`, toasts. It links
to the pipeline via `route('deals')` and expects to live at route name `leads`.

**Deal (additive only)**: `STAGE_PROBABILITIES` const, `activities()`
morphMany, `winProbability()`, `probability` cast, plus the
`2026_09_12_000103` migration adding the nullable `probability` column.

## What audit already covered — and was NOT rebuilt

`Deal` is already in the `AuditObserver` list (AppServiceProvider), so every
create/update/stage-move on a deal is in `activity_log`. CRM therefore did
**not** get a change log: `crm_activities` records only the *planned* side —
the call to make Thursday, the meeting that changed no field. "Who moved this
deal to lost and when" remains an audit-trail question with one answer.
`Lead` is a new model and is **not** observed (`app/Providers` is off-limits
to this phase); adding `Lead::class` to the observer list in
AppServiceProvider is a one-line orchestrator follow-up worth making.

## Permissions

Both new policies (`LeadPolicy`, `CrmActivityPolicy`) declare group `deals`,
so **no new permission keys are needed**. Argument: a lead is the front half
of the same pipeline, worked by the same people — a role that may see the
board should not be blind to where its deals come from, and "may chase leads
but not deals" is not a real arrangement in the businesses this serves. If
that separation is ever wanted, add a `Leads` group to
`App\Support\Permissions` and change the two `group()` methods; nothing else
moves. **Note**: the policies rely on Laravel's convention-based discovery
(`App\Policies\LeadPolicy` etc.). If discovery is disabled, add them to
`AuthServiceProvider::$policies` — two lines.
