## The opt-in mechanism

`items.tracking_mode` — `none` (default) | `batch` | `serial`. Every existing
product gets `none`, which is exactly the behaviour that existed before: no
lot, no serial, no expiry. `BatchLedger` throws for a `none` product rather
than inventing a lot for it, so tracking cannot half-happen.
Reservations work for any product but are only consulted if someone calls
them — a business that never reserves sees `available == on hand` forever.

## Permissions to add (`app/Support/Permissions.php` + `RolePermissionSeeder`)

- `stock.batches.view` — see lots, serials and expiry reports
- `stock.batches.manage` — record lots/serials, write off expired stock
- `stock.reservations.manage` — reserve and release stock

Suggested roles: owner/admin/manager get all three; staff gets
`stock.batches.view` and `stock.reservations.manage`.

## Wiring points you may want (deliberately NOT done)

1. **Sales.** `StockLedger::move()` writes one movement per line with a null
   batch. For a traceable product it could call
   `BatchLedger::pick($item, $location, $qty, 'sale', $actor, $document)`
   instead. I left it alone because picking can *fail* (nothing unexpired in
   stock) and making document issue throw is a behaviour change that belongs
   to whoever owns the issuing flow.
2. **Goods receipts.** `GoodsReceipt` lines could carry a lot number / serial
   list and call `BatchLedger::receive()` / `receiveSerials()`.
3. **Dashboard.** An "expiring soon" tile from `expiringWithin()`.
4. **Scheduler.** `StockReservations::sweepExpired()` daily. Purely cosmetic —
   `holding()` already ignores lapsed reservations, so stock is never stuck
   even if it never runs.
