## 5. Two follow-ups I deliberately did NOT make, because the files are yours

Both are one-line changes and both are real gaps. A debit note is a receivable
(`DocumentType::isReceivable()` returns true for it) but two existing AR features
still filter on `->invoices()`, which is `ofType(invoice)` only — so a debit note
is currently invisible to them:

**a) `app/Support/Aging.php`, `receivable()` (line ~63):**

```php
// was: ->invoices()
->whereIn('type', [DocumentType::Invoice->value, DocumentType::DebitNote->value])
```

**b) `app/Services/Dunning.php`, `runForCompany()` (line ~90):**

```php
// was: Document::query()->invoices()->outstanding()
Document::query()
    ->whereIn('type', [DocumentType::Invoice->value, DocumentType::DebitNote->value])
    ->outstanding()
```

Alternatively add a `scopeReceivables()` to `App\Models\Document` and use it in
both places, plus in `Statement::openDocuments()` and `CollectionsQueue::accounts()`
where the same `whereIn` is currently inlined. That is the version I would
prefer; I left `Document.php` alone because it is shared.

Note `CollectionsQueue` already handles the *other* half of this trap: the
`outstanding()` scope does not filter by type, so a credit note (which has an
open balance by construction) would be counted as a debt. The queue pulls credit
notes in only to net them off as `credit_available`. If you touch `Aging`, check
it does not acquire the same bug.

## 6. Decisions a reviewer should know about

- **A debit note is issued immediately**, like a credit note. A draft that says a
  customer owes more changes nothing while looking as though it has.
- **It never moves stock.** A debit note is money: an undercharge, a price
  correction, a rebilled freight cost, a late fee. Where extra goods really left
  the shelf, that is a second sale and belongs on a second invoice.
- **It has a due date** (customer terms, default 14 days), unlike a credit note
  which has none. Without one it could never be overdue, and dunning and the
  collections queue would never see it.
- **Tax**: against an invoice, the split uses that invoice's own effective rate
  (so a zero-rated sale does not acquire 19.25% TVA on correction). Standalone,
  the default is no tax — a late-payment charge is compensation, not
  consideration for a supply, and is outside VAT scope in the OHADA/CEMAC
  regimes this platform serves. An explicit `$taxRate` overrides that.
- **There is no cap on debit notes per invoice**, deliberately — unlike credit
  notes, which cannot exceed the invoice. Crediting more than was charged is
  always an error; charging more can be entirely legitimate (a fee, then a
  second fee). `DebitNotes::debitedTotal()` is there for a UI that wants to show
  the running total.
- **Statements are built from document totals plus payments, never balances.**
  Using balances would net a payment into the invoice line and then count it
  again as its own line. It also means a statement for a *past* period is right
  about that period.
- **The collections queue is not stored** — same reasoning as the aging report.
  The only thing persisted is what a human did, in `collection_activities`.
- **Queue ordering** is three bands (broken promise → no arrangement → open
  promise), then overdue amount weighted 1/2/4/8 by aging bucket. Old money
  outranks merely large money, and somebody who said "Friday" is not rung on
  Thursday.
- **Known limitation, inherited**: the aging figures on a statement use each
  document's *current* balance, so a statement for a past period ages what is
  open *today*. Same trade-off `App\Livewire\Reports\Aging` documents; fixing it
  needs balance history the platform does not store.
