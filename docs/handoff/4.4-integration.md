# Phase 4.4 — Notification rules engine

Configurable notifications: on event X matching conditions Y, tell recipients Z
on channels C — with per-person preferences, noise control, and a log that
answers "nobody told me".

---

## Inventory: what already notified, before this phase

Taken before writing anything, because the brief for this phase is *make the
existing path configurable*, not *add a second one*.

**There was exactly one path, and it is Laravel's.** Every notification in the
product ends at `$notifiable->notify(...)` with `via()` returning `mail` and/or
`database`. Nothing sends its own mail, and nothing writes the `notifications`
table by hand.

| Layer | Where | What it did |
|---|---|---|
| Laravel notifications | 23 classes in `app/Notifications/` | `mail` + `database`, all queued |
| The bell | `App\Livewire\Notifications\Bell` + `notifications` table | Polls every 30s. No websockets in this stack. |
| Company fan-out | `App\Support\NotifyCompany::about()` / `::recipients()` | "Every active member holding permission P" |
| Automation | `ActionRunner::notify()` → `AutomationNotification` | `notify_user` / `notify_role`, hard-coded to mail + bell |
| Direct calls | 24 call sites (dunning, billing, invitations, low stock, tickets, payments, partners, forms, reviews, admin, auth) | `$user->notify(...)` |

Two things follow from that, and both shaped the design:

1. **There was nowhere to configure any of it.** A recipient could not mute
   anything; a business could not decide who hears about what. The channels a
   message used were a hard-coded array inside each notification class.
2. **`ActionRunner::notify()` was the closest thing to a rules engine already
   in place.** So it was extended, not duplicated — it now routes through the
   new dispatcher and obeys the same preferences as everything else. Its test
   was updated to assert `RuleNotification` rather than `AutomationNotification`.

**`App\Notifications\AutomationNotification` is now unused.** It is left on
disk rather than deleted, because deleting a notification class while queued
jobs referencing it may still be in flight is how a deploy loses messages.
Delete it once the queue has drained.

## Integration the orchestrator has to do

### 1. Listener registration — **do nothing, deliberately**

`RunNotificationRules` is **already live** via Laravel's event discovery, which
is on in this app and picks up anything in `app/Listeners` whose `handle()`
type-hints an event. `ListenerRegistrationTest` fails if a second registration
is ever added.

> **Pre-existing bug found while checking this.** `app/Providers/AppServiceProvider.php`
> explicitly registers four listeners that discovery *also* finds, so each is
> registered twice and **runs twice on every domain event**:
> `RunAutomationRules`, `TranslateDocumentWorkflowEvents`,
> `PostApprovedExpenseClaims`, `SyncApprovedRequisitions`.
> `Event::getListeners(DomainEvent::class)` returns 11 entries for 7 classes.
> Every automation rule currently fires twice — including `notify_user`, which
> means duplicate alerts today. Fix: delete those four `Event::listen()` lines.
> Out of my file ownership.

### 2. Schedule the digest

In `routes/console.php`:

```php
Schedule::command('notifications:digest')->hourly();
```

Hourly is the right grain: it is the finest resolution a quiet-hours window
needs, and the summary frequency is then configured in exactly one place
rather than baked into every held row. **If the host has no cron at all,
nothing is lost silently** — held rows sit in `notification_deliveries` with
`status = deferred` and are visibly waiting on the rules screen.

### 3. Routes

```php
Route::get('settings/notification-rules', NotificationRules::class)->name('settings.notification-rules');
Route::get('settings/notifications', NotificationSettings::class)->name('settings.notifications');
```

Inside the authenticated + `SetCurrentCompany` group, alongside
`settings/webhooks`.

### 4. Permissions

Uses `workflows.manage` for the rules screen (Owner + Administrator) and
**no gate at all** on the personal preferences screen.

**Recommended change, which I could not make:** add `'Notifications' =>
['manage']` to `App\Support\Permissions::CATALOGUE`, grant it to Owner and
Administrator in `RolePermissionSeeder`, and swap the two `authorize()` calls
in `app/Livewire/Settings/NotificationRules.php`. `workflows.manage` is a
borrowed key — it happens to have the right holders, which is not the same as
being the right key.

The preferences screen is ungated on purpose: an alert somebody cannot switch
off gets a mail filter written against the whole sender, and that filter hides
the critical ones too. Offering the switch is what keeps the critical channel
working.

### 5. `config/modules.php` placement

**None.** Notifications are a platform service, not a module. A business cannot
switch them off any more than it can switch off permissions — and a module
whose alerts silently stopped because someone toggled "Notifications" would be
a support call, not a feature. Individual *categories* are switched off per
person on the preferences screen, which is the switch that actually makes
sense.

### 6. Guides

No guide was written — `app/Support/Guides.php` and `resources/guides/` are
outside my ownership and `GuidesTest` fails if a file and its catalogue entry
disagree. Two are needed: **Notification rules** (administrator) and **Your
notifications** (everyone). Source material is in this document and the class
docblocks.

## The hard part: preventing noise

A notification that fires on every event is noise, noise gets muted, and a
muted channel is worse than no channel. Four levers, because they fail
differently and no one of them is sufficient:

| Lever | Kills | Loses |
|---|---|---|
| **Deduplication** (`dedupe_minutes`) | Machine-generated repeats — a status field touched five times in a minute is five events and one piece of news | Nothing. The repeats were not information. |
| **Digest** (per person) | Human-generated volume — twelve real alerts in a morning | Nothing said, only immediacy |
| **Quiet hours** (per person) | Interruptions at the wrong time | Nothing — messages are **held and released**, never dropped |
| **Mute** (per person, per category, per channel) | Whole classes of thing you do not own | Everything in that category — the only lossy lever, which is why it is the one that is per-category rather than per-rule |

And one escape hatch: **`severity = critical` bypasses all four.** Exactly one
level may, and that is load-bearing. If `normal` could break through too, a
mute would mean nothing; mutes that mean nothing get replaced with sender-wide
mail filters, and those hide the critical ones. Keeping precisely one
unmutable level is what makes the other three safe to offer — and the
preferences screen says so in plain words, because somebody who cannot see why
an alert keeps arriving assumes the switch is broken.

The dedupe fingerprint includes the record **and the title**, so two invoices
never suppress each other and "approved" never suppresses "rejected" about the
same invoice a minute later.

## No paid vendors — plainly

**Nothing here requires an API key, an account, or a per-message fee.** No
package was added. Only two channels are implemented: **in-app** (the existing
bell) and **email** (the existing mailer).

SMS and WhatsApp are **catalogued and marked unavailable** in
`App\Support\NotificationChannels`. A rule may name one; the dispatcher writes
a `suppressed / channel_unavailable` row and sends nothing. It never pretends
to have sent — that is the one failure a delivery log cannot recover from.

### What a future gateway has to implement

The abstraction is deliberately thin. A channel is a business-facing key mapped
onto a **Laravel notification channel**, and the product keeps exactly one
delivery path — `$user->notify()`. To add SMS:

1. Write a Laravel channel class with `send($notifiable, $notification)`,
   registered via `Notification::extend('sms', …)` in a provider.
2. Have it read `$notification->toSms($notifiable)` — add that method to
   `RuleNotification` and `NotificationDigest`.
3. In `NotificationChannels::CATALOGUE`, set `'driver' => 'sms'` and
   `'available' => true`.
4. Route the number: `routeNotificationForSms()` on `User` — `users.phone`
   already exists.

**Nothing else changes.** Preferences, quiet hours, digests, deduplication and
the delivery log all key on the channel string and pick the new one up for
free. The preferences screen renders `NotificationChannels::available()`, so
the column appears on its own.

A channel class that sent its own mail or its own HTTP request *outside*
Laravel's notification system was the alternative and would have been worse: it
would have its own retries, its own failures and its own idea of what an
unsubscribe means, and "why did this arrive twice" would have two places to
look.

## Design decisions worth challenging

**Two rule tables, not one.** `notification_rules` sits beside
`automation_rules` rather than becoming a sixth automation action. They answer
different questions — "what should the product now do" versus "who should now
be told" — and the notification one needs five columns automation has no use
for. The cost is real: two very similar admin screens, and a business that
wants both writes two rules. The alternative was one table with a mostly-null
half, and one broken rule row able to stop the other engine running.

**Preferences are per company, not per user.** Somebody who works for two
businesses configures each separately. That is more work for them and correct
for everyone else — the categories that matter differ by business. The digest
command deliberately crosses back: it groups by person and channel, not by
company, so a two-business user gets **one** summary. Splitting it by tenant
would put the count back up, and the count is the whole point.

**Quiet hours are evaluated in the app timezone (UTC).** There is no
`companies.timezone` column and no per-user timezone in this product. For a
Cameroon-based business that is a one-hour offset, which is wrong but not
badly. **This is the weakest thing shipped** and should get a real column.

**The blanket preference row uses `''`, not `NULL`.** MySQL treats two NULLs as
distinct in a unique index, so a nullable scope column would let one person
accumulate twenty conflicting blanket rows with the resolver picking whichever
came back first. `enabled` and `mode` *are* nullable, and that is a different
thing — null there means "inherit", so setting quiet hours on a category does
not also switch that category on.

**Digest rows are marked sent before the notification is queued.** A second
run of the command while the first is still working must not send the same
summary twice. The trade is that a crash between the update and the send loses
that summary — chosen over a duplicated digest, which is exactly the noise the
digest exists to prevent.

**A rule that reaches nobody still stamps `last_fired_at`.** Otherwise an
administrator debugging "this rule never fires" cannot tell "the event never
happened" from "it happened and reached nobody" — and those have opposite fixes.

**Nothing was migrated.** The 24 existing direct `notify()` call sites still
send unconditionally and are not covered by preferences or the delivery log.
That is the honest state of it: converting `InvoiceOverdueNotification` and the
rest to rule-driven messages is a follow-up, and doing it half-way would have
been worse than not starting. Each one needs a category, a severity, and a
decision about whether a business may switch it off.

**Queued, degrading to sync.** `RuleNotification` and `NotificationDigest`
implement `ShouldQueue`. With `QUEUE_CONNECTION=sync` — shared hosting with no
worker — they run inline: slower, still correct. Assuming a daemon fails by
going quiet, and a notification system that fails quietly is the worst option
on the table.
