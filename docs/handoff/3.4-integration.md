## Naming note

`App\Support\SupplierAccount` is the *report* (our record of a supplier's
account). `App\Models\SupplierStatement` is the *document the supplier sent us*.
The names are deliberately different because the two things are: one is derived
from our bills, the other is the counterparty's claim and is stored verbatim.

## 1. Permissions — needed in `App\Support\Permissions` and `RolePermissionSeeder`

Suggested keys, following the existing naming:

```
payables.schedule.view      see the payment schedule and runs
payables.schedule.manage    build runs, add/skip lines
payables.run.approve        approve a run  (separate from manage — this is the control)
payables.run.execute        release the money
suppliers.statement.view    a supplier's account statement
suppliers.reconcile         import supplier statements and match lines
```

`payables.run.approve` should NOT be granted to whoever gets
`payables.schedule.manage` by default. `PaymentScheduler::execute()` refuses a
run that is not approved, and that refusal is the only thing standing between a
misclick and an emptied bank account. Splitting the two permissions is what
makes it a real control rather than a speed bump.

## 5. Contracts a caller needs to know

### `PaymentSchedule`

```php
new PaymentSchedule($company, payOn: null, reserve: 0.0, horizonDays: 14);
$schedule->bills();          // Collection, banded + scored, worst first
$schedule->plan($cash);      // $cash null => taken from CashForecast
```

`plan()` returns `pay_on, cash_on_hand, reserve, cash_available, items[],
total_scheduled, total_outstanding, shortfall, suppliers_paid`. Each item
carries `decision` of `fund` | `part` | `defer`.

### `PaymentScheduler`

```php
$run = $scheduler->buildRun($schedule, ['scheduled_for' => …, 'method' => 'bank', 'cash' => …], $actor);
$scheduler->addBill($run, $expense, $amount);
$scheduler->skip($item, 'reason');
$scheduler->approve($run, $actor);
$scheduler->execute($run, $actor);   // ['paid' => int, 'total' => float, 'failed' => []]
```

`execute()` returns rather than throws on individual lines that were settled or
voided between approval and execution — it skips them with a reason. The other
twenty suppliers should not wait on one already-paid invoice. Show the `failed`
array to the user; it is not an error, it is a finding.

### `SupplierReconciler`

```php
$statement = $reconciler->import($supplier, $header, $rows, $actor);
$reconciler->addLines($statement, $rows);      // re-import safe, fingerprinted
$reconciler->parseCsv($contents);              // forgiving headers, debit/credit folded
$reconciler->autoMatch($statement);            // reference AND amount, exactly one candidate
$reconciler->suggestionsFor($line);            // scored, for a human to accept
$reconciler->match($line, $expense);
$reconciler->dispute($line, 'why');
$reconciler->summary($statement);
```

## 6. Decisions a reviewer should know

1. **The schedule takes only the receipts side of `CashForecast`.** The payments
   side of the forecast *is* the payables this schedule is deciding on. Letting
   the forecast subtract them here would count every bill twice — once as a
   forecast outflow, again as a plan line — and leave a business that could pay
   convinced it could not. `PaymentSchedule::projectedCash()` = forecast opening
   + forecast receipts up to the pay week.

2. **Age weights are gentle (1.0 → 3.0), unlike collections (1.0 → 8.0).** A
   supplier's patience does not fall off a cliff at ninety days the way a
   customer's willingness to pay does. A steep curve here would starve every
   recent bill to clear one ancient dispute.

3. **Part-funding the bill the cash runs out on**, rather than skipping to a
   smaller one that fits. Floor is 1 XAF — no minor unit, so anything less is
   noise.

4. **`reserve` is not cash.** It is cash the plan is forbidden to touch. It is
   the only mechanism keeping a heavy payables week from eating payroll, so it
   belongs in the UI as a first-class field, not an advanced option.

5. **Approval is a separate state from draft**, and `execute()` refuses an
   unapproved run. See the permissions note above.

6. **Reconciliation never edits either side.** Matching records that a statement
   line and one of our bills describe one event. Nothing writes to `expenses`.
   `SupplierStatement::closing_balance` is never recomputed from the lines —
   when a supplier's own total disagrees with their own lines that is a finding
   (`summary()['statement_self_consistent']`), and overwriting it erases it.

7. **`autoMatch` requires reference AND amount, and exactly one candidate.** A
   right reference with the wrong money is a dispute, not a match; two bills
   that both fit is the duplicate-billing case a person must look at. Silently
   matching either is how an overcharge gets paid every month thereafter.

8. **Statement status is derived, never set by hand** (`refreshStatus`). A
   statement frozen at "reconciled" because somebody clicked a button in March
   is worse than no status at all.

9. **Payment settlement goes through `ExpenseRecorder::settle()`**, not through
   new posting code. One posting path — so a bill paid in a run and a bill paid
   by hand land in the books identically. No journal rows are written directly
   anywhere in this phase.

10. **Skipped run lines are kept, not deleted.** "Why was this supplier not
    paid" is the question a payment run gets asked, and a deleted line cannot
    answer it.

## 7. Known limitation

`SupplierAccount::openBills()` ages bills using today's `amount_paid`, not the
paid-to-date as at the end of the reported period — the same simplification the
customer-side `Statement::openDocuments()` makes with `documents.balance`. The
running balance and closing balance ARE correct for a past period; only the
aging block on a back-dated statement reflects today. Worth fixing on both sides
at once if it ever matters, so the two stay comparable.

## Notes for whoever reviews the screens

1. **Cash and reserve are the first two fields on the schedule**, live-bound, and
   every fund/part/defer mark moves when they do. A zero reserve is called out
   in words — it means the wages are on the table.
2. **Approve and release are never adjacent.** Approve is an outlined brand
   button in its own block; release is a red-bordered block further down that
   only exists once the run is approved, and it opens a confirmation spelling out
   the amount, the supplier count and the date before anything happens.
3. **`execute()`'s refusal is surfaced, not swallowed** — a `RuntimeException`
   from any service call becomes an `addError` or a flashed error, following
   `Assets\Movements::transfer()`.
4. **Someone with `payables.manage` but not `payables.approve` sees no approve
   control** and is told the run is waiting on someone else; the action itself
   also refuses (403), so hiding it is presentation rather than the control.
5. **The reconciliation summary is the top of the screen**, not a footer: their
   balance, ours, the difference, and the two directions side by side. A
   supplier whose own lines disagree with their own total is reported in place
   and never corrected.
